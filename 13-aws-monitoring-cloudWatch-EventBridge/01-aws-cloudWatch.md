# AWS CloudWatch – Monitoring Services

## 1. What is Monitoring?

Monitoring is the process of continuously observing infrastructure, applications, servers, databases, and networks to understand their health, performance, and availability.

In a production environment, applications must run continuously. We need to monitor whether servers are healthy, applications are responding, and resources are being utilized properly.

### Why do we need monitoring?

1. **Performance monitoring:** Monitor CPU, memory, disk, and network utilization.
2. **Availability:** Identify whether servers and applications are healthy.
3. **Troubleshooting:** Identify the reasons for application failures.
4. **Early detection:** Identify problems before they become major incidents.
5. **Alerting:** Send notifications when a configured threshold is breached.
6. **Capacity planning:** Understand resource utilization and plan infrastructure.
7. **Cost optimization:** Identify underutilized and overutilized resources.
8. **High availability:** Help maintain application availability and reliability.

### Real-time example

Imagine an e-commerce website running on an AWS EC2 instance.

- Suddenly, CPU utilization reaches 95%.
- The application becomes slow.
- Customers cannot access the website properly.
- Without monitoring, the DevOps engineer might not know about the issue until customers complain.

With monitoring, we can detect the issue and receive alerts automatically.

**Interview answer: Why do we need monitoring?**

Monitoring helps us continuously observe the health and performance of infrastructure and applications. It allows DevOps engineers to identify issues early, troubleshoot failures, maintain availability, and improve application reliability.

## 2. What is Amazon CloudWatch?

Amazon CloudWatch is an AWS monitoring and observability service.

It collects and monitors metrics, logs, and events from AWS resources and applications.

It helps us understand the operational health and performance of AWS infrastructure.

### Example

If we launch an EC2 instance, CloudWatch can monitor:

- CPU utilization
- Network In
- Network Out
- Disk read operations
- Disk write operations
- Instance status checks

We can create alarms based on these metrics and receive notifications when conditions are met.

## 3. Important CloudWatch Components

### 3.1 CloudWatch Metrics

Metrics are numerical measurements collected over time.

Examples:

| Metric | Example Value |
|---|---:|
| CPU Utilization | 75% |
| Memory Utilization | 80% |
| Disk Utilization | 65% |
| Network In | 500 MB |
| Network Out | 300 MB |

CloudWatch metrics are organized using:

- Namespace
- Metric name
- Dimensions

Example:

```text
Namespace: AWS/EC2
Metric Name: CPUUtilization
Dimension: InstanceId
```

### 3.2 CloudWatch Logs

Logs contain records of activities and events generated by applications and operating systems.

Example:

```text
2026-11-18 10:00:00 INFO Application started
2026-11-18 10:01:00 INFO User login successful
2026-11-18 10:02:00 ERROR Database connection failed
```

CloudWatch Logs helps collect and investigate these records centrally.

Important terminology:

| Term | Meaning |
|---|---|
| Log Group | Collection of log streams |
| Log Stream | Sequence of log events from one source |
| Log Event | Individual log record |
| Retention | How long logs are stored |

### 3.3 CloudWatch Alarms

CloudWatch Alarms monitor metrics against configured thresholds.

Example:

```text
EC2 CPU Utilization > 80%
          |
          v
   CloudWatch Alarm
          |
          v
      ALARM State
          |
          v
     Amazon SNS
          |
          v
    Email Notification
```

### 3.4 CloudWatch Dashboards

Dashboards display multiple metrics in one visual interface.

For example, a production dashboard can display:

- EC2 CPU utilization
- EC2 network traffic
- RDS database connections
- ALB request count
- Lambda errors

### 3.5 CloudWatch Agent

CloudWatch Agent collects additional operating-system-level metrics and log files.

Examples:

- Memory utilization
- Disk utilization
- Disk free space
- Operating system logs
- Application logs

**Important:** EC2 basic monitoring provides metrics such as CPU and network utilization. Memory utilization is not available by default. We need to install and configure the CloudWatch Agent to collect memory and filesystem metrics.

## 4. CloudWatch Alarm – Important Concepts

| Term | Meaning |
|---|---|
| Namespace | Container that groups metrics, e.g. AWS/EC2 |
| Metric | Measurement being monitored |
| Statistic | Calculation applied to metric data |
| Period | Time interval over which metric data is aggregated |
| Threshold | Value used to determine whether an alarm condition is breached |
| Datapoints to alarm | Number of breaching datapoints required to trigger the alarm |
| Evaluation period | Number of periods considered during alarm evaluation |
| SNS | Simple Notification Service used to send notifications |

### 4.1 Alarm States

CloudWatch alarms have three important states.

**ALARM**

The metric has crossed the configured alarm threshold for the required evaluation datapoints.

**OK**

The metric is within the configured threshold.

**INSUFFICIENT_DATA**

CloudWatch does not have enough metric data to determine the alarm state.

### 4.2 Threshold Type

**Static threshold**

We manually define the threshold value.

Example:

```text
CPUUtilization >= 80%
```

**Anomaly detection**

CloudWatch uses an expected metric range based on historical patterns to identify unusual behavior.

### 4.3 Statistic

Statistic determines how CloudWatch aggregates metric data.

Common statistics:

| Statistic | Meaning |
|---|---|
| Average | Average value |
| Maximum | Highest value |
| Minimum | Lowest value |
| Sum | Total value |
| SampleCount | Number of data samples |

Example:

CPU utilization values:

```text
10%, 20%, 30%
```

Average:

```text
(10 + 20 + 30) / 3 = 20%
```

### 4.4 Period

Period defines the time interval over which CloudWatch aggregates metric data.

For EC2 CPU monitoring:

- Basic monitoring generally provides data at 5-minute intervals.
- Detailed monitoring provides data at 1-minute intervals.
- High-resolution metrics can support periods below one minute when the metric supports them.

For the EC2 CPU practical, use a 1-minute period with detailed monitoring enabled.

A 30-second high-resolution alarm can incur additional charges and requires compatible high-resolution metric data.

### 4.5 Datapoints to Alarm

Example:

```text
1 out of 1
```

One breaching datapoint out of one evaluated datapoint is sufficient to trigger the alarm.

Example:

```text
3 out of 5
```

Three out of the last five evaluated datapoints must breach the threshold to trigger the alarm.

### 4.6 Missing Data Treatment

CloudWatch provides options for handling missing metric data:

- Treat missing data as missing
- Treat missing data as good
- Treat missing data as bad
- Ignore missing data

The practical screenshot uses:

```text
Treat missing data as missing
```

This means CloudWatch does not automatically treat missing metric data as healthy or unhealthy.

## 5. What is Amazon SNS?

Amazon SNS stands for Simple Notification Service.

It is a messaging and notification service used to deliver messages to subscribers.

SNS supports different destinations:

- Email
- SMS
- AWS Lambda
- Amazon SQS
- HTTP/HTTPS endpoints

### CloudWatch and SNS integration

Example:

1. EC2 CPU utilization exceeds 80%.
2. CloudWatch detects the threshold breach.
3. CloudWatch alarm changes to ALARM state.
4. CloudWatch publishes a notification to SNS.
5. SNS sends an email to the subscribed DevOps engineer.

**Important:** The SNS email subscription must be confirmed before notifications can be delivered.

# 6. Hands-on Practical 1 – Create a CloudWatch CPU Utilization Alarm

## Objective

Create a CloudWatch alarm for an EC2 instance and configure an email notification through an existing SNS topic.

### Practical Configuration

| Parameter | Value |
|---|---|
| AWS Region | US West (Oregon) |
| Service | CloudWatch |
| Data Source | Metrics |
| Type | Classic |
| Namespace | AWS/EC2 |
| Metric | CPUUtilization |
| Instance Name | cloudwatch-server-01 |
| Statistic | Average |
| Threshold Type | Static |
| Condition | Greater/Equal |
| Threshold in Screenshot | 5% |
| Datapoints to Alarm | 1 out of 1 |
| Missing Data | Treat missing data as missing |
| SNS Topic | skoda-autoscaling-practicals-01 |
| Alarm State Trigger | In alarm |

## Step 1: Launch an EC2 Instance

1. Open AWS Management Console.
2. Navigate to EC2.
3. Launch an EC2 instance.
4. Give the instance a name:

```text
cloudwatch-server-01
```

5. Select Amazon Linux.
6. Choose an instance type.
7. Configure the key pair and security group.
8. Launch the instance.

Make sure the EC2 instance is running.

## Step 2: Open CloudWatch

1. Search for CloudWatch in AWS Console.
2. Open CloudWatch.
3. Select Alarms from the left navigation.
4. Click Create alarm.

## Step 3: Specify Metric and Conditions

The first page shows three data sources:

- Metrics
- Logs
- Alarms

Select:

```text
Metrics
```

Under Type, select:

```text
Classic
```

Click Edit under Metric.

Select:

```text
Namespace: AWS/EC2
Metric Name: CPUUtilization
Dimension: InstanceId
Instance: cloudwatch-server-01
```

Select the EC2 instance you want to monitor.

## Step 4: Configure Metric Settings

The practical screenshot shows:

| Setting | Selected Value |
|---|---|
| Metric | CPUUtilization |
| Instance ID | i-076261574b409ecdb |
| Instance Name | cloudwatch-server-01 |
| Statistic | Average |
| Period | 30 seconds |

**What is Average?**

Average calculates the average CPU utilization for the selected period.

**What is Period?**

Period defines the time interval over which CloudWatch aggregates the metric data.

For normal EC2 CPU monitoring, use a compatible 1-minute or 5-minute period depending on monitoring configuration.

## Step 5: Configure Alarm Conditions

The screenshot shows:

```text
Threshold Type: Static
Condition: Greater/Equal
Threshold: 5
Datapoints to Alarm: 1 out of 1
Missing Data: Treat missing data as missing
```

**Threshold Type – Static**

We manually define the threshold value.

**Condition – Greater/Equal**

The alarm triggers when CPU utilization is greater than or equal to the configured threshold.

**Threshold – 5**

The screenshot uses 5%.

| CPU Utilization | Alarm Result |
|---:|---|
| 2% | OK |
| 4% | OK |
| 5% | ALARM |
| 10% | ALARM |
| 80% | ALARM |

The 5% threshold is useful for demonstrating alarm behavior, not as a normal production CPU threshold.

For production, we might start with 80% and adjust according to the application's performance baseline.

**Datapoints to Alarm – 1 out of 1**

One breaching datapoint out of one evaluated datapoint is sufficient to trigger the alarm.

**Missing Data Treatment**

The screenshot selects:

```text
Treat missing data as missing
```

This means CloudWatch does not automatically assume missing metric data represents a healthy or unhealthy condition.

## Step 6: Configure Alarm Actions

The second step is Configure actions.

Select:

```text
Alarm State Trigger: In alarm
```

Under SNS topic selection, choose:

```text
Select an existing SNS topic
```

Select the existing topic:

```text
skoda-autoscaling-practicals-01
```

The screenshot also shows an email endpoint configured on that topic.

Additional actions available:

- Lambda action
- Auto Scaling action
- EC2 action
- Systems Manager action
- Investigation action

For this practical, SNS email notification is sufficient.

## Step 7: Add Alarm Details

The third step is Add alarm details.

Alarm name:

```text
cloudwatch-server-01-cpu-alarm
```

Alarm description:

```text
Monitors EC2 CPU utilization and sends an SNS
email notification when CPU reaches or exceeds
the configured threshold.
```

Tags are optional.

## Step 8: Preview and Create

The final step is Preview and create.

Verify:

- Namespace: AWS/EC2
- Metric: CPUUtilization
- Instance: cloudwatch-server-01
- Statistic: Average
- Period: Correctly configured
- Threshold: Greater than or equal to 5%
- SNS Topic: skoda-autoscaling-practicals-01
- Alarm Name: cloudwatch-server-01-cpu-alarm

Click Create alarm.

**Expected Result:**

The CloudWatch alarm is created and starts evaluating the selected EC2 metric.

# 7. Hands-on Practical 2 – Test CloudWatch Alarm

## Objective

Generate CPU load on the EC2 instance and verify whether the CloudWatch alarm changes its state.

### Step 1: Connect to EC2

```bash
ssh -i your-key.pem ec2-user@YOUR_PUBLIC_IP
```

### Step 2: Install Stress Utility

For Amazon Linux 2023:

```bash
sudo dnf install stress-ng -y
```

### Step 3: Generate CPU Load

```bash
stress-ng --cpu 2 --timeout 300s
```

This generates CPU load for five minutes using two CPU workers.

### Step 4: Monitor CloudWatch

Navigate to:

```text
CloudWatch → Alarms
```

Select:

```text
cloudwatch-server-01-cpu-alarm
```

Observe the CPU utilization graph and alarm state.

### Step 5: Verify Notification

When the metric breaches the configured threshold for the required evaluation period:

1. CloudWatch changes the alarm state to ALARM.
2. CloudWatch invokes the configured SNS action.
3. SNS sends an email notification.
4. Check the subscribed email inbox.

After the stress process finishes, CPU utilization should reduce and the alarm can return to OK after sufficient non-breaching datapoints.

**Important:** Do not expect an immediate email at the exact moment CPU rises. Metric collection, alarm evaluation and notification delivery take time.

# 8. Hands-on Practical 3 – Monitor EC2 Memory and Disk Utilization

## Why do we need CloudWatch Agent?

EC2 basic monitoring provides infrastructure metrics such as CPU and network utilization.

Memory utilization and filesystem usage are operating-system-level metrics.

To collect memory and disk utilization, we need to install and configure CloudWatch Agent.

### Step 1: Install CloudWatch Agent

For Amazon Linux 2023:

```bash
sudo dnf install amazon-cloudwatch-agent -y
```

### Step 2: Configure IAM Role

Create an IAM role for EC2 with the required CloudWatch permissions.

Attach the AWS managed policy:

```text
CloudWatchAgentServerPolicy
```

Attach this IAM role to the EC2 instance.

### Step 3: Run Configuration Wizard

```bash
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-config-wizard
```

Follow the prompts to configure memory, disk and log collection.

### Step 4: Start CloudWatch Agent

Use the actual configuration file path generated by the wizard.

Example:

```bash
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
-a fetch-config \
-m ec2 \
-c file:/opt/aws/amazon-cloudwatch-agent/bin/config.json \
-s
```

### Step 5: Check Agent Status

```bash
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
-a status
```

### Step 6: Verify Metrics

Navigate to:

```text
CloudWatch → Metrics → CWAgent
```

You can monitor:

- mem_used_percent
- disk_used_percent
- disk_free
- disk_used

# 12. AWS Monitoring Services – Comparison

| Service | Main Purpose | Example |
|---|---|---|
| CloudWatch | Monitoring and observability | CPU reaches 90% |
| CloudTrail | API activity auditing | Who terminated EC2? |
| AWS Config | Configuration tracking | Security group changed |
| AWS X-Ray | Distributed tracing | Find slow microservice |
| Trusted Advisor | Best-practice recommendations | Identify cost and security improvements |
| AWS Health | AWS service health events | AWS maintenance notification |
| EventBridge | Event-driven automation | Trigger Lambda when an event occurs |

### CloudWatch vs CloudTrail vs AWS Config

**CloudWatch:** How is my infrastructure performing?

**CloudTrail:** Who performed an action in AWS?

**AWS Config:** What configuration changed?

# 13. Common Troubleshooting Scenarios

| Problem | What to Investigate |
|---|---|
| CPU alarm not triggering | Metric, threshold, period and evaluation settings |
| No email notification | SNS subscription confirmation and topic permissions |
| Memory metric unavailable | CloudWatch Agent installation and configuration |
| Logs not appearing | Agent status, IAM permissions and log configuration |
| Alarm shows insufficient data | Metric availability, dimensions and missing data settings |
| Dashboard has no graph | Correct namespace, metric and instance dimensions |

### Production Monitoring Best Practices

1. Don't create alarms with unnecessarily low thresholds.
2. Choose evaluation periods based on application requirements.
3. Configure and confirm SNS subscriptions.
4. Monitor memory and disk, not only CPU.
5. Monitor application errors and latency in addition to infrastructure metrics.
6. Consider CloudWatch costs, especially high-resolution alarms, custom metrics and log ingestion.
7. Configure alarm notifications for appropriate state transitions.
8. Avoid alert fatigue by creating meaningful alarm thresholds.
