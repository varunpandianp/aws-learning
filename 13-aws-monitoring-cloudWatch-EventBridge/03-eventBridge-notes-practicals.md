# AWS EventBridge – Complete Study Notes & Hands-on Practicals

## 1. What is Amazon EventBridge?

Amazon EventBridge is a serverless event-driven service provided by AWS.

It receives events from AWS services, applications, and SaaS partners, evaluates those events against configured rules, and routes matching events to targets.

**In simple words: EventBridge listens for events and triggers an action when a matching event occurs.**

### Example

1. An EC2 instance is launched.
2. EC2 generates an event.
3. EventBridge receives the event.
4. EventBridge checks its configured rules.
5. If the event matches a rule, EventBridge triggers the configured target.
6. The target can send an email through SNS or execute a Lambda function.

---

## 2. Why do we need EventBridge?

In production environments, many AWS resources continuously generate events.

Examples:

- EC2 instance launched.
- EC2 instance stopped.
- EC2 instance terminated.
- EBS volume created.
- EBS snapshot completed.
- Auto Scaling instance launched.
- AWS service configuration changed.

Without event-driven automation, DevOps engineers may need to check these changes manually.

EventBridge helps automate responses to these events.

### Real-world DevOps use cases

| Scenario | EventBridge Action |
|---|---|
| EC2 instance stopped | Send SNS email notification |
| EC2 instance terminated | Trigger Lambda |
| EC2 instance launched | Execute automation |
| EBS volume event | Send notification |
| Spot instance interruption | Trigger recovery workflow |
| AWS API activity detected | Send security notification |

## 3. How does EventBridge work?

### Important components

| Component | Purpose |
|---|---|
| Event | Something that happens in AWS |
| Event Source | Service that generates the event |
| Event Bus | Receives events |
| Event Pattern | Defines which events should match |
| Rule | Connects an event pattern to one or more targets |
| Target | Action executed when an event matches |
| Archive | Stores events for possible replay |
| Replay | Replays previously archived events |

### EventBridge Architecture

```text
              AWS Event Sources
        EC2 | S3 | RDS | Lambda | CloudTrail
                       |
                       v
                  Event Bus
                       |
                       v
                EventBridge Rules
                       |
                       v
                 Event Pattern
                       |
             +---------+---------+
             |         |         |
             v         v         v
            SNS      Lambda     SQS
             |         |         |
             v         v         v
           Email    Automation  Queue
```

## 4. Types of Event Buses

EventBridge supports three main types of event buses.

### 4.1 Default Event Bus

The default event bus receives events from AWS services in your account.

Example:

```text
EC2 → EventBridge Default Event Bus
```

Use it to monitor events generated by AWS resources.

### 4.2 Custom Event Bus

A custom event bus receives events from your own applications or other event producers.

Example:

```text
Application → Custom Event Bus → Lambda
```

Use it when building application-specific event-driven architectures.

### 4.3 Partner Event Bus

A partner event bus receives events from supported third-party SaaS partners.

Example:

```text
SaaS Application → Partner Event Bus → AWS Target
```

## 5. What is an Event Pattern?

An event pattern is a JSON configuration that tells EventBridge which events it should match.

Example: Monitor EC2 instance state changes.

```json
{
  "source": ["aws.ec2"],
  "detail-type": [
    "EC2 Instance State-change Notification"
  ]
}
```

This matches EC2 instance state-change notifications.

### Monitor only stopped instances

```json
{
  "source": ["aws.ec2"],
  "detail-type": [
    "EC2 Instance State-change Notification"
  ],
  "detail": {
    "state": ["stopped"]
  }
}
```

This matches only EC2 instances entering the stopped state.

### Understanding Event JSON

Example EC2 event:

```json
{
  "version": "0",
  "id": "7bf73129-1428-4cd3-a780-95db273d1602",
  "detail-type": "EC2 Instance State-change Notification",
  "source": "aws.ec2",
  "account": "123456789012",
  "time": "2026-11-18T10:00:00Z",
  "region": "us-west-2",
  "resources": [
    "arn:aws:ec2:us-west-2:123456789012:instance/i-1234567890abcdef0"
  ],
  "detail": {
    "instance-id": "i-1234567890abcdef0",
    "state": "stopped"
  }
}
```

### Important event fields

| Field | Meaning |
|---|---|
| source | AWS service that generated the event |
| detail-type | Type of event |
| account | AWS account ID |
| region | AWS Region |
| time | Event timestamp |
| resources | Related resource ARNs |
| detail | Event-specific information |
| instance-id | EC2 instance ID |
| state | Current EC2 instance state |

## 6. EC2 Events in EventBridge

For this practical, we will focus on EC2 events.

### EC2 instance state changes

| EC2 State | Meaning |
|---|---|
| pending | Instance is starting |
| running | Instance is running |
| stopping | Instance is stopping |
| stopped | Instance is stopped |
| shutting-down | Instance is terminating |
| terminated | Instance is terminated |

Other EC2-related events include:

- EC2 Spot Instance Interruption Warning
- EC2 Spot Instance Rebalance Recommendation
- EC2 AMI State Change
- EBS Volume Notification
- EBS Snapshot Notification
- EBS Multi-Volume Snapshots Completion Status
- EC2 Fast Launch State-change Notification
- Capacity Reservation events

**Important distinction:**

EC2 service events and EC2 API activity are not exactly the same.

- Direct EC2 service events notify us about resource and service events.
- CloudTrail events report API activity, such as RunInstances, StopInstances, StartInstances and TerminateInstances.
- Auto Scaling lifecycle events use the `aws.autoscaling` source.

The pattern `{"source":["aws.ec2"]}` does not capture every event related to EC2 or Auto Scaling.

# 7. Practical 1 – Create an EventBridge Rule for EC2 Events

## Objective

Create an EventBridge rule that listens for EC2 events and sends email notifications through an SNS topic.

### Architecture

```text
EC2 Events
    |
    v
EventBridge Default Event Bus
    |
    v
EC2 Event Rule
    |
    v
SNS Topic
    |
    v
Email Notification
```

### Step 1: Create SNS Topic

1. Open AWS Management Console.
2. Search for SNS.
3. Open Simple Notification Service.
4. Select Topics.
5. Click Create topic.
6. Select Standard.
7. Enter topic name:

```text
ec2-event-notifications
```

8. Click Create topic.

### Step 2: Create SNS Email Subscription

1. Open the newly created topic.
2. Select Create subscription.
3. Select protocol: Email.
4. Enter your email address.
5. Click Create subscription.
6. Open your email inbox.
7. Click Confirm subscription.

**Important:** Without confirming the email subscription, SNS cannot deliver notifications to that email endpoint.

### Step 3: Open EventBridge

1. Search for EventBridge in AWS Console.
2. Open Amazon EventBridge.
3. Select Event buses.
4. Open the Default event bus.
5. Select Rules.
6. Click Create rule.

### Step 4: Configure Rule Details

| Parameter | Value |
|---|---|
| Rule Name | ec2-all-events-rule |
| Description | Monitor EC2 events and send SNS notifications |
| Event Bus | default |
| Rule Type | Rule with an event pattern |

Click Next.

### Step 5: Configure Event Pattern

Select:

```text
Event Source: AWS services
AWS Service: EC2
```

For a broad EC2-source event pattern, use:

```json
{
  "source": ["aws.ec2"]
}
```

This matches events whose source is `aws.ec2`, including applicable direct EC2 service events and EC2 API events delivered through CloudTrail.

Click Next.

### Step 6: Configure Target

Select:

```text
Target Type: AWS service
Target: SNS topic
Topic: ec2-event-notifications
```

Click Next.

Review the configuration and create the rule.

### Expected Result

Your EventBridge rule is created and enabled.

It will listen for matching EC2 events on the default event bus.

### Step 7: Test the EventBridge Rule

Navigate to:

```text
EC2 → Instances
```

Choose a test EC2 instance.

If the instance is running:

1. Select the instance.
2. Click Instance state.
3. Select Stop instance.
4. Confirm the action.

The instance will go through:

```text
running → stopping → stopped
```

EventBridge receives EC2 state-change notifications.

The SNS topic should receive matching event notifications, and you should receive emails.

Start the instance again:

```text
stopped → pending → running
```

This generates more state-change events.

**Note:** Event delivery is normally near real time, but direct AWS service event delivery is best effort.

# 8. Practical 2 – Create a Rule Only for EC2 Stopped Events

In the previous practical, we created a broad EC2 event rule.

Now let's create a specific rule that only monitors stopped instances.

### Event Pattern

```json
{
  "source": ["aws.ec2"],
  "detail-type": [
    "EC2 Instance State-change Notification"
  ],
  "detail": {
    "state": ["stopped"]
  }
}
```

Rule name:

```text
ec2-stopped-event-rule
```

Target:

```text
SNS → ec2-event-notifications
```

### Expected Behavior

| Instance Action | Notification |
|---|---|
| Start instance | No |
| Stop instance | Yes |
| Instance enters running | No |
| Instance enters stopped | Yes |
| Terminate instance | No, unless another configured pattern matches |

This is useful when you want to alert the DevOps team whenever an EC2 instance unexpectedly stops.

# 10. Practical 4 – Monitor EC2 API Calls Using CloudTrail

This is an important practical because monitoring instance state changes and monitoring who performed an API action are different use cases.

For example:

- Who launched an EC2 instance?
- Who stopped an EC2 instance?
- Who terminated an EC2 instance?
- Who modified an EC2 security group?

CloudTrail records API activity.

### Step 1: Open CloudTrail

Navigate to:

```text
AWS Console → CloudTrail → Event history
```

Search for management events such as:

```text
RunInstances
StartInstances
StopInstances
TerminateInstances
ModifyInstanceAttribute
```

### Step 2: Create EventBridge Rule

Navigate to:

```text
EventBridge → Rules → Create rule
```

Rule name:

```text
ec2-api-activity-rule
```

Event pattern:

```json
{
  "source": ["aws.ec2"],
  "detail-type": [
    "AWS API Call via CloudTrail"
  ],
  "detail": {
    "eventSource": ["ec2.amazonaws.com"],
    "eventName": [
      "RunInstances",
      "StartInstances",
      "StopInstances",
      "TerminateInstances",
      "ModifyInstanceAttribute"
    ]
  }
}
```

Target:

```text
SNS → ec2-event-notifications
```

Now the rule matches the selected EC2 API operations recorded through CloudTrail.

**Important:** Ensure the relevant CloudTrail management events are available for delivery to EventBridge. The event pattern filters events; it does not enable CloudTrail recording by itself.

# 11. EventBridge vs CloudWatch vs CloudTrail

These three services are frequently confused in interviews.

| Service | Main Responsibility | Example |
|---|---|---|
| EventBridge | Event routing and automation | EC2 stopped → SNS |
| CloudWatch | Monitoring metrics, logs and alarms | CPU utilization exceeds 80% |
| CloudTrail | Auditing AWS API activity | Who stopped EC2? |

### Real-world example

Suppose an EC2 instance is terminated.

- CloudTrail records who performed the termination API call.
- EventBridge receives the relevant termination event and routes it to SNS.
- CloudWatch monitors infrastructure metrics and alarm conditions.

# 13. AWS CLI – EventBridge Commands

### List EventBridge rules

```bash
aws events list-rules
```

### List rules on default event bus

```bash
aws events list-rules \
  --event-bus-name default
```

### Describe a rule

```bash
aws events describe-rule \
  --name ec2-all-events-rule
```

### Enable a rule

```bash
aws events enable-rule \
  --name ec2-all-events-rule
```

### Disable a rule

```bash
aws events disable-rule \
  --name ec2-all-events-rule
```

### List rule targets

```bash
aws events list-targets-by-rule \
  --rule ec2-all-events-rule
```

### List event buses

```bash
aws events list-event-buses
```

### Test an event pattern

Create `ec2-pattern.json`:

```json
{
  "source": ["aws.ec2"],
  "detail-type": [
    "EC2 Instance State-change Notification"
  ],
  "detail": {
    "state": ["stopped"]
  }
}
```

Create `ec2-event.json` containing a representative event:

```json
{
  "version": "0",
  "id": "example-event-id",
  "detail-type": "EC2 Instance State-change Notification",
  "source": "aws.ec2",
  "account": "123456789012",
  "time": "2026-11-18T10:00:00Z",
  "region": "us-west-2",
  "resources": [],
  "detail": {
    "instance-id": "i-1234567890abcdef0",
    "state": "stopped"
  }
}
```

Run:

```bash
aws events test-event-pattern \
  --event-pattern file://ec2-pattern.json \
  --event file://ec2-event.json
```

The command returns whether the supplied event matches the event pattern.

### Delete a rule

First remove its targets:

```bash
aws events remove-targets \
  --rule ec2-all-events-rule \
  --ids "1"
```

Then delete the rule:

```bash
aws events delete-rule \
  --name ec2-all-events-rule
```

# 14. EventBridge Troubleshooting

| Problem | What to Check |
|---|---|
| EventBridge rule not triggering | Verify event pattern and event source |
| SNS email not received | Confirm SNS subscription |
| Rule disabled | Check rule state |
| Target not invoked | Check target configuration and permissions |
| CloudTrail API event missing | Check CloudTrail management event delivery |
| Wrong EC2 instance matches | Add instance ID filtering |
| No event in another Region | Check the Region where the event occurred |
| Duplicate notifications | Check overlapping rules and target configurations |

### Production Best Practices

1. Use specific event patterns instead of broad patterns when possible.
2. Avoid unnecessary notifications for every AWS event.
3. Configure SNS email subscriptions properly.
4. Check target invocation failures and retry behavior.
5. Use CloudTrail for API auditing.
6. Remember that direct AWS service event delivery can be best effort.
7. Keep IAM permissions restricted to the actions required by each target.
8. Monitor EventBridge target delivery failures.
